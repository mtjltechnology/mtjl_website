How it works

The test does not break because a button moved

Traditional automation ties the test to a CSS selector. Change the class, break the suite, and the next sprint turns into test maintenance instead of new coverage. Here a language model reads the page the way a person would and looks for the element by what it is, not by where it used to be. Because the model is the one interpreting, the case works in whatever language your team writes in.

Three routes to the element before it fails

  • First the accessibility tree, which changes less often than the CSS class
  • If that fails, a search by the text that describes the element
  • As a last resort, a check against the screenshot of what it is seeing
  • Replans after every navigation, without losing track of the test case

Evidence ready for your client's audit

  • Screenshots before, after and on error, step by step
  • A record of what was planned and what was executed, in JSON, ready to attach to the report
  • Password fields and sensitive data masked in the capture
  • Automatic retry, so a test does not fail on a network hiccup
App

An app for people who write tests all day

Installer for macOS, Windows and Linux. It runs on its own, with no server and no login, so the pilot starts on one analyst's machine instead of in an infrastructure meeting. It does not require Node installed either: the app loads what it needs.

Editor and terminal built in

File explorer, the same editor as VS Code, and a real terminal, with the folder locked to the project root. Anyone who already uses VS Code learns nothing new.

Git on the same screen

Branch, changed files, commit, push, pull and diff without dropping to the terminal. The test case is versioned alongside the code it tests.

The assistant proposes, you accept

The AI suggests the change and shows the diff. Nothing is written until someone approves it, file by file.

Local runs in parallel

One to eight tests at a time, with the output streaming in the terminal. A regression suite that used to take the afternoon fits in a coffee break. Data lives in a project folder, versioned with the code.

Coverage

Three browsers, three kinds of test, our own driver

No Playwright and no Selenium in the middle: the conversation is straight with the browser. And no browser is downloaded behind your back, it uses what is already installed on the machine, which settles half the discussion with information security.

Chrome, Edge and Firefox

Same test case and same API on both engines, Chromium and Gecko. It walks shadow DOM and same-origin iframes.

Web, API and responsive

Interface testing, authenticated HTTP requests, and layout checks across ten screen sizes, portrait and landscape. One product instead of three tools to reconcile.

Fits your pipeline without a rewrite

The same engine three ways: imported in code, called from the continuous integration pipeline, or opened in the app. The case written in the app is the case that runs in the pipeline.

Governance

When your client audits your quality process

Banking, healthcare and public sector ask for proof, not screenshots pasted in a document. The multi-team server adds exactly that to the engine: who wrote it, who approved it, what ran and when.

Four-eyes approval

Test cases are versioned, and whoever writes one cannot approve their own. Execution is blocked until an approved version exists.

Five roles, and every team in its own lane

Read, author, approve, execute and administer. Each team sees only its own tests, which matters when a software house serves competing clients.

A trail that exposes an altered record

Every entry chains to the previous one, and a dedicated call verifies the integrity of the whole trail. Touching history becomes detectable.

AI spend with a ceiling

A model catalogue with usage limits and consumption on screen, plus organisation, teams, projects, audit, and encrypted backup with restore drills. The AI bill does not surprise you at month end.

Frequently asked questions

What a quality team asks before switching tools

Does the test break when the screen layout changes?

That is not the point of failure here. The language model reads the page the way a person would and finds the element by what it is, not by a fixed CSS selector, and it replans after every navigation. That is where the team stops burning sprints on maintenance.

Do I need Playwright or Selenium?

No. PilotQA AI talks straight to the browser through its own driver, with no Playwright or Selenium in the middle.

Which browsers does it support?

Chrome, Edge and Firefox, with the same API and the same test case on both engines, Chromium and Gecko.

Do I need Node installed?

No. The desktop app, for macOS, Windows and Linux, loads what it needs on its own. It is an analyst-level install, not an infrastructure project.

How does governance work for a QA team?

Four-eyes approval, where whoever writes the case cannot approve their own, five access roles per team, and an audit trail that exposes any record altered after the fact.
